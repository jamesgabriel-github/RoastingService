# Fix: Unify booking codes on one shared RS-YYMMDD-NNN sequence

**Type:** Fix
**Status:** verified
**Branch:** fix/booking-code-generator

## The problem

`BookingCodeGenerator` (online customer bookings/orders, codes shaped
`RS-####`) found "the next number" by reading whichever booking has the
highest `id` and parsing its code as if it were always `RS-####`. That broke
the moment the most recent booking in the table was actually a walk-in
booking, whose code is the differently-shaped `WB-YYMMDD-NNN` (generated by
the separate `WalkInCodeGenerator`, which counts bookings per-date instead of
parsing a code string). `(int) substr('WB-260928-002', 3)` silently parsed as
`260928`, producing garbage `RS-` numbers that could collide.

This surfaced while seeding local booking test data: interleaving `WB-` and
`RS-` codes in one run produced a duplicate-key crash on `bookings.code`.
It was a latent production bug too - any time the last booking created
happened to be a walk-in, the next online booking got a bogus code.

## The fix

Centralized on one code shape and one counter instead of two generators with
two shapes. Every booking, online or walk-in, now gets `RS-YYMMDD-NNN`,
counted per-date directly from the database. With only one shape in the
column, there's nothing left for a generator to misparse. Nothing in the
codebase branched on the `WB-`/`RS-` prefix, so this was a low-risk
simplification, not a functional behavior change beyond the code's own text.

`BookingCodeGenerator` was rewritten to be exactly what `WalkInCodeGenerator`
already was, minus the prefix swap; `WalkInCodeGenerator` was deleted
entirely.

## Build steps

- [x] 1. **Rewrite `BookingCodeGenerator`, delete `WalkInCodeGenerator`,
  update call sites and tests.** `BookingCodeGenerator::next()` now takes the
  booking's `preferred_pickup_at` and returns `RS-YYMMDD-NNN`, counting
  `Booking::whereDate('preferred_pickup_at', ...)->count() + 1` under the same
  transaction-scoped Postgres advisory lock as before. Updated call sites:
  `WalkInController` (both `storeRoasting`/`storeShop`, swapped injected type),
  customer `BookingController::store`, customer `OrderController::store`
  (both now pass `$request->validated('preferred_pickup_at')`), and
  `database/seeders/BookingSeeder.php` (dropped its local workaround for the
  bug and now uses the one real generator for every booking).
  **Done when:** `composer test` passes in full and `vendor/bin/pint` is
  clean.
  **Status:** done.

## Verify

- `composer test` (from `backend/`): pass, 274/274, including the rewritten
  `BookingCodeGeneratorTest` (renamed from `WalkInCodeGeneratorTest`, with a
  new regression test proving an unrelated existing code shape can't corrupt
  the next generated code) and updated format assertions in
  `AdminWalkInBookingTest`, `BookingManagementTest`, and
  `ShopOrderManagementTest`.
- `vendor/bin/pint --test` (from `backend/`): pass.
- Manual: ran `php artisan db:seed --class=BookingSeeder` against the local
  dev database - all 13 seeded bookings received clean, sequential
  `RS-260928-001` through `RS-260928-013` codes with no collisions.

## Independent review

Not required. `qualityGates.regular.independentReview` is `when-sensitive`;

auth, payments, or a security boundary - and every affected booking-creation
flow is covered by the existing, unchanged test suite. `/audit independent
current` remains available on request.
